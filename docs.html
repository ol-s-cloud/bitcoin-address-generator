Online or offline.

COBRA is a local-first cryptographic research tool. These docs explain the live browser engine, the original Python methodology, offline address generation, cold-storage architecture, offline transaction signing, and the boundary between public blockchain data and controlling secrets.

1. Address derivation

entropy → private key → secp256k1 public key → SHA-256 → RIPEMD-160 → version/checksum → Base58Check → Bitcoin address

The public address may be shared. The private key/WIF is the controlling secret and must not be published, logged, sent to analytics, or disclosed to an agent.

2. COBRA Offline

Bitcoin address derivation itself does not require an internet connection. An offline computer can generate entropy, derive a private key and public address, and retain the secret locally. Network access is required later to observe blockchain state or broadcast a transaction.

Design principle: the offline machine owns secrets; the online machine observes public state and broadcasts signed transactions.

COBRA's offline package is designed as a static, self-contained copy of the address lab. No API, account, KYC, remote database or server-side private-key processing is required.

3. Cold storage

Cold storage means keeping signing keys away from network-connected systems. A practical architecture separates an offline signer from an online watch-only environment. The online side can monitor addresses and prepare transactions without possessing the private keys.

OFFLINE / COLD ONLINE / WATCH-ONLY private keys public descriptors/addresses signing blockchain monitoring transaction verification ←PSBT→ transaction construction NO broadcast broadcast to Bitcoin network

Cold storage reduces network exposure; it does not eliminate risks from compromised software, weak entropy, physical theft, malicious removable media, incorrect backups, or signing the wrong transaction.

4. Offline transactions with PSBT

COBRA's planned transaction workflow uses Partially Signed Bitcoin Transactions (PSBT), the standard interchange format described by BIP 174. An online device constructs an unsigned PSBT. The PSBT is moved to the offline signer by QR code or removable media. The offline device verifies destination, amount and fee, signs locally, and returns the signed transaction. Only the online machine broadcasts it.

ONLINE: create unsigned PSBT ↓ QR / removable media OFFLINE: inspect → verify → sign ↓ signed PSBT / transaction ONLINE: broadcast → Bitcoin peer-to-peer network
Not yet a production wallet: COBRA should not present transaction signing as production-safe until the signer has deterministic test vectors, pinned dependencies, reproducible builds and independent security review.

5. Terminal / Python

The original repository contains the Python research lineage. COBRA already has a CLI skeleton with address generation and validation commands. The next maintained CLI layer can add explicit offline workflows, safer secret-handling defaults, PSBT inspection and eventually offline signing without modifying the historical notebook.

For a genuinely air-gapped machine, installation should also be possible from pre-downloaded, checksummed release artifacts rather than requiring live pip access.

6. Working with AI agents

Agents can be useful around the cryptographic boundary without being entrusted with private keys. A COBRA-compatible agent could monitor public addresses, watch confirmations and fees, prepare unsigned PSBTs, explain transaction data, flag anomalies, manage research/news workflows, or coordinate developer APIs.

Agent boundary: agents should operate on public data and unsigned transaction intent. Private keys, seed phrases and WIF secrets should remain inside a trusted signer and should never be placed in prompts, model context, telemetry or remote agent tools.
AGENT / ONLINE LAYER observe → analyse → prepare unsigned intent → request human approval ↓ OFFLINE TRUST BOUNDARY verify → authorize → sign

This separation also creates a future research direction for policy-controlled autonomous finance: agents can propose actions while cryptographic authorization remains constrained by human approval, hardware policy, multisignature rules or other explicit controls.

7. Storage of value & future hardware

COBRA can evolve from an educational address laboratory toward an ecosystem of audited offline software, developer tooling and eventually dedicated signing hardware. Potential commercial layers include supported enterprise tooling, developer/API services, audited offline distributions, research partnerships and, only after substantial security engineering and certification work, dedicated hardware signing devices.

The objective is not to claim that the current website is a hardware wallet. The current product demonstrates and documents the cryptographic method; custody-grade products require a materially higher assurance standard.
